# Решения по неоднозначностям и противоречия задания

## Противоречия в задании

1. Доступность 99,9% допускает около 43 минут простоя в месяц, а RTO равен 45 минутам. Один инцидент на пределе RTO уже превышает месячный бюджет доступности. В Task1 основной сценарий отказа (потеря узла, пода или зоны) закрывается автоматическим переключением за минуты, без восстановления из бэкапа. RTO 45 минут относится к худшему сценарию: восстановлению базы из резервной копии.
2. В описании текущей архитектуры ins-product-aggregator уже запрашивает предложения по ОСАГО, а в задании 4 ОСАГО назван новым продуктом с отдельным сервисом osago-aggregator. Принято: ОСАГО целиком в osago-aggregator.
3. Задание 4 требует сохранить подход получения данных о продуктах и одновременно показывать предложения сразу по приходу ответа. Принято: связь сервисов через брокер, доставка предложений в веб-приложение через SSE.
4. Лимит в задании 6 равен 10 запросам в минуту, договоренность с партнером равна 20 RPS (1200 запросов в минуту). Конфигурация выполнена по заданию 6, расхождение отмечено в комментарии nginx.conf.
5. В части 1 задания 2 пункты 5, 6 и 7 повторяют друг друга, команда minikube service стоит внутри пункта про HPA, хотя относится к пункту про Service.
6. ins-comp-settlement раз в сутки собирает реестр оформленных страховок у core-app и раз в месяц отправляет перечень в страховые компании. Это два разных процесса.

## Задание 1. Технологическая архитектура

1. Масштабирование горизонтальное. Вертикальное упирается в размер одной ВМ, требует перезапуска и не убирает единую точку отказа. Горизонтальное дает запас под рекламную кампанию и работает вместе с HPA и Cluster Autoscaler.
2. Три зоны доступности региона ru-central1: ru-central1-a, ru-central1-b, ru-central1-d. Три зоны нужны для кворума etcd и Patroni: при потере одной зоны большинство сохраняется.
3. Независимый кластер Managed Kubernetes в каждой зоне, а не один растянутый. Отказ или неудачное обновление одного кластера не задевает остальные, нет межзонных задержек внутри control plane, кластеры обновляются по очереди. Манифесты одинаковые, развертывание во все три кластера идет из одного репозитория.
4. Вход клиентов. Статика веб-приложения отдается через Cloud CDN из Object Storage: узлы CDN стоят в регионах, поэтому время загрузки страниц не зависит от местоположения пользователя. API идет через Application Load Balancer (L7) с узлами во всех трех зонах.
5. Фейловер на уровне клиента: active-active, все три зоны принимают трафик. ALB проверяет health check ingress каждого кластера и при отказе зоны перестает слать в нее запросы. CDN при недоступности источника отдает закешированную статику.
6. Балансировка между сервисами внутри кластера: Service Kubernetes, проверки readiness и liveness. Доступ к БД через HAProxy, который проверяет REST API Patroni и ведет запись только на лидера.
7. База данных: PostgreSQL под управлением Patroni, хранилище конфигурации кластера etcd (три узла, по одному в зоне). Лидер в одной зоне, синхронная реплика в соседней, асинхронная в третьей. При отказе лидера Patroni повышает синхронную реплику без потери подтвержденных транзакций.
8. Резервное копирование: непрерывная архивация WAL в Object Storage с archive_timeout не более 5 минут и ежедневный полный бэкап. Это закрывает RPO 15 минут даже при потере всех трех узлов БД.
9. Шардирование не применяется. Объем данных 50 GB помещается на один узел, нагрузка на чтение распределяется на реплики. Шардирование усложнило бы транзакции оформления и восстановление.
10. Мониторинг и алерты обязательны: при текущей архитектуре команда узнавала о падении от пользователей. Без алертов RTO и 99,9% недостижимы.
